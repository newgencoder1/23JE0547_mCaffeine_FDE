## 3. Architecture and request journey

```
 Browser (HTML + vanilla JS)          Render free web service (Docker)              Supabase
 ─────────────────────────           ────────────────────────────────              ───────────────────────
 login / list / PO page  ── HTTPS ──▶ Flask + gunicorn                     ──SQL──▶ Postgres
   session cookie (HttpOnly,          ├─ auth.py         login, 401                  users, purchase_orders (UNIQUE po_number)
   signed, SameSite=Lax)              ├─ permissions.py  every 403/404 rule          po_line_items, po_actions (append-only)
                                      ├─ workflow.py     state machine + history
                                      ├─ validation.py   money/date parsing, checks
                                      ├─ extraction.py   pdfplumber → (Tesseract)
                                      ├─ storage.py      ─────────── REST ──────────▶ Storage: private bucket po-pdfs
                                      └─ health.py       /health → SELECT 1
                                      logs → stdout → Render log viewer
```

**Upload journey** (`POST /api/pos/upload`, in `app/pos.py` `upload_po`):

1. **Browser.** The creator picks a PDF. JS checks it is ≤ 5 MB and sends `multipart/form-data` with the session cookie.
2. **Backend: auth.** `login_required` loads the user from the database, or returns **401**. `require_creator_role` returns **403** for approver-only users.
3. **Backend: input checks.** The file must be ≤ 5 MB (Flask's `MAX_CONTENT_LENGTH` gives a friendly 413) and must start with `%PDF-`.
4. **Storage.** The original bytes go to the private bucket under a random key `pos/<uuid>.pdf`. They are never written to the server's disk; Render's disk is ephemeral anyway. If storage fails, the user gets a friendly 502 and the server logs the cause.
5. **Extraction.** `extract_po()` reads the text layer, decides whether it is usable, parses header and lines, and falls back to OCR if allowed. A bad PDF never raises an error; it returns `readable=false`.
6. **Database.** One transaction inserts the DRAFT PO and its lines. If the PO number already exists, the **UNIQUE constraint** refuses it. The draft is then saved without a number, and the response says "PO number … already exists" without revealing whose PO it is. On any other failure the stored PDF is deleted again.
7. **Response.** `201` with the PO, its check results and the extraction message. The browser opens `/po/<id>`, which shows the editable form with failed fields highlighted, the line-items table, the checks panel and the history.

Opening the PDF later (`GET /api/pos/<id>/pdf`) re-checks visibility and then redirects to a signed link that expires after 5 minutes. The storage key never reaches the browser.

## 4. Readable vs unreadable PDFs (`app/extraction.py`)

`assess_text()` checks whether the text **makes sense**, not just how much there is:

* **Almost no characters (< 40)** → a scan or image-only PDF.
* **Junk ratio > 3 %** → `(cid:NN)` glyph placeholders plus characters outside normal text (`¤§¶†`…). This is what a broken font encoding produces.
* **Fewer than 3 PO words** (purchase, order, total, qty, rate, vendor, date…) → a "gibberish" layer, e.g. letters shifted by a bad character map. Sample 4 fails both of the last two tests.
* Usable text that still yields neither a PO number nor a total is also treated as unreadable.

Unreadable files are **never** used to fill the form. The user sees a clear message, a blank form and the original PDF, and types the values in by hand (`extraction_method = manual`).

**OCR.** `pdftoppm` renders pages 1–2 at 300 dpi in grayscale, and `tesseract --psm 4` reads them. psm 4 ("one column, variable sizes") kept the boxed header grid readable; psm 6 lost the labels. The OCR text then goes through the **same** `assess_text` → `parse_po_text` → `run_checks` pipeline. OCR is accepted only if it finds both a PO number and a total. The only clean-up is mapping `% ¥ € £` in front of an amount back to `₹`, a misread I observed. Digits are **never** "corrected": wrong digits must fail the maths checks. Where it fails: a misread `₹` became `=`, and that row could not be parsed. The tool then warns "this line looks like an item but could not be read", and the PO-maths check fails because the lines no longer add up. Other weak spots are faint or tilted phone photos (no deskew yet), handwriting and stamps over numbers, and the 1 ↔ 7 and 0 ↔ 8 confusions. Line maths and PO maths catch those because a single wrong digit breaks the arithmetic.

## 5. Permissions: 401 / 403 / 404 and where each check lives

All rules live in **`app/permissions.py`** (one function per rule). The routes in `app/pos.py` and the transitions in `app/workflow.py` call them **before** touching data. The UI's `permissions` flags only decide which buttons to show; every rule is re-checked on each request, so direct `curl` and Postman calls get the same answers (`tests/test_workflow_api.py`).

| # | Rule | Status | Code |
|---|---|---|---|
| 1 | No valid login | **401** | `auth.py` `login_required` (l.55–73) wraps every `/api/*` route except login/logout |
| 2 | Only Approvers approve/reject | **403** | `permissions.require_approver` called first in `workflow.approve` (l.84) / `workflow.reject` (l.97); also on queue lists (`pos.py` l.211) |
| 3 | Nobody decides their own PO (incl. `lead1`) | **403** | `permissions.require_not_own_po` (`workflow.py` l.87, l.100), **plus** `AND created_by <> %s` inside the UPDATE itself |
| 4 | Creators see/edit/submit only their own POs | **404** | `permissions.load_visible_po` / `can_view` (every route that takes an id), `require_owner` (edit `pos.py` l.316, submit `workflow.py` l.70, discard l.380) |
| 4 | Edit only while DRAFT/REJECTED | **409** | `permissions.require_editable` (`pos.py` l.317) and `WHERE status IN ('DRAFT','REJECTED')` |
| 5 | Only SUBMITTED can be decided; second approve refused | **409** | `workflow.approve`/`reject` status check, plus the atomic `UPDATE … WHERE id = ? AND status = 'SUBMITTED'` in `workflow._transition` (l.40–46) |
| 6 | Rejection needs a non-empty reason | **400** | `workflow.reject` (l.104), whitespace-only counts as empty |
| 7 | Approvers see SUBMITTED from all creators, never edit | queue / **403** | `pos.list_pos` `view=queue`; `require_owner` refuses approvers on PUT |
| — | Checks re-run on submit | **422** | `workflow.submit` runs `validation.run_checks` on the **stored** data (l.75–77) |
| — | Duplicate PO number | **409** | `db/schema.sql` `po_number TEXT UNIQUE`; caught via `db.is_unique_violation` (`pos.py` l.269, l.326) |

**Why 404, not 403, for another creator's PO:** a 403 would confirm that PO id exists and belongs to someone else. A 404 gives the same answer as "no such PO", so ids can't be probed. That is the same reason the duplicate message never says whose PO it is. Approvers can open any PO that has left DRAFT. Drafts stay private to their creator.

**Atomicity.** Each transition is one transaction: a conditional `UPDATE … RETURNING id` plus one `INSERT` into `po_actions`. If two approvers click at the same moment, Postgres row locking lets the first one win. The second `UPDATE` then matches 0 rows and gets 409. `tests/pg_verify.sh` proves this on real Postgres with two concurrent sessions. **History is append-only** in three layers: there is no API route to change it, there is no UI control, and database triggers reject `UPDATE`, `DELETE` and `TRUNCATE` on `po_actions`. Timestamps come from the database clock (`now()`).

## 6. Key decisions and libraries

* **Flask + plain HTML/JS, no framework or starter template.** Small enough to read end to end; every rule is on the server anyway. No starter template or UI library was used.
* **Libraries:** `pdfplumber` (text layer with layout), Tesseract + Poppler CLI (OCR), `bcrypt` (cost 12), `psycopg` 3 (Postgres), `requests` (Supabase Storage REST, so no SDK), `gunicorn`.
* **Money as integer paise, using `Decimal`.** `₹1,24,500.00`, `Rs. 124500`, `INR 1,24,500`, `124,500` and `Rs 1,24,500/-` all become `12450000`. Floats never appear, and a test proves `0.10 + 0.20 == 0.30`. Tolerance is ₹1, i.e. 100 paise.
* **Dates:** stored as Postgres `DATE` (ISO) and shown as DD-MM-YYYY. The parser always reads day-month-year: `15-11-2026`, `15/11/2026`, `15.11.2026`, `15 Nov 2026`.
* **PO numbers are normalised** (trimmed, upper-case) before saving, so `po-2026-001 ` can't slip past the UNIQUE constraint.
* **Parse errors vs check failures:** a value that can't be read (e.g. "twelve lakh") is refused with 422 and not saved. Business-check failures can be saved as a draft but block submit. "Line items not checked" is shown when a PO has no lines, rather than passing silently.
* **Sessions:** a signed HttpOnly cookie that stores only the user id; the user is re-loaded from the database each request. Unknown usernames still run bcrypt, so timing doesn't reveal which usernames exist.
* **Logs:** UTC timestamp, level and request id on every line, e.g. `2026-11-27T14:45:44.630Z INFO [req=24fceba15a03] refused POST /api/pos/1/approve -> 403: You cannot approve…`. The same request id appears in the user's error message, so one user report maps to one log line. Stack traces go to the log only.
* **Testing:** 76 pytest tests (rules, checks, extraction). `tests/pg_verify.sh` and `tests/pg_explain.py` replay every SQL statement against real Postgres 16. A headless-browser walkthrough caught one UI bug: CSS was overriding the `hidden` attribute, so locked POs showed edit buttons. The server refused those clicks anyway.

**Free-tier limits and how they are handled:** Render spins down after 15 idle minutes, so the first request takes about 50 s. A pinger (UptimeRobot/cron-job.org on `/health`) can be enabled during the review window. Render's disk is ephemeral, which is why nothing is stored on it. Supabase pauses a free project after about 7 days of low database activity; the `/health` ping runs a real query, which keeps it active, and the project can be resumed from the dashboard. Free Supabase storage is 1 GB, enough for many thousands of PO PDFs.

## 7. Monday, 10 a.m.: "Approve is failing and 12 POs are due by noon"

1. **Ask for the message and reference.** Every error shows a `request_id`. A specific refusal (403/409) means the rules are working, not a crash.
2. **Open `/health`.** If it shows `503 "database": "unreachable"`, the app is up but can't reach Postgres. The most likely cause on the free plan is that Supabase paused the project over a quiet weekend: resume it in the dashboard (a minute or two) and re-check `/health`. Other causes are a rotated DB password or a changed pooler host, which means updating `DATABASE_URL` in Render. `missing_config` lists any required env var names that are empty, and `version` shows which commit is live. `/health?deep=1` also checks the storage bucket.
3. **If health is OK, search the Render logs** for the request id, or for `approve`: `refused … 403` means the user is not an approver or created the PO (e.g. lead1 on their own POs, so another approver must act). `409` means the PO is no longer SUBMITTED. `401` everywhere after a deploy means `SECRET_KEY` changed and everyone was logged out: log in again and keep the key fixed. `ERROR unhandled error` with a stack trace means a code bug.
4. **Config and deploys.** Compare Render's env vars against `.env.example`. Check whether a deploy happened since Friday (Render → Events). If it did and the timing matches, roll back with one click; Render keeps the two previous deploys on free.
5. **Unblock the business first.** If one approver account is the problem, another approver can clear the 12 POs. Once fixed, confirm by approving one PO and checking its history line.

## 7a. Known limitations and next steps

* Line items must start with a SKU-like code; rows without codes aren't parsed and must be added by hand. Only the first 5 pages are read (OCR: first 2).
* OCR runs inside the request (a few seconds per page). Next step: a background job queue, deskewing, and per-field confidence from Tesseract's TSV output to highlight doubtful digits.
* No pagination, password reset, user admin or login rate-limiting yet. Logout clears the cookie, but a stolen cookie stays valid until it expires (8 h). Next step: server-side session revocation.
* One database connection per request is fine at this scale; next step is a connection pool. Next: email notifications for the approval queue, an audit export (CSV), and an approval limit per approver.
